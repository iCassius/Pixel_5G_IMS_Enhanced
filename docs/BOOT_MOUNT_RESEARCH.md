## 源码解释与阶段选择

- `module/post-fs-data.sh` 先验证守卫文件，然后执行 `pixel_framework_eligible`。现场到达 vendor/product 判断，说明平台检查及前置完整性检查已通过。
- 两组均先执行 `pixel_modem_matches`，成功后才计算该组文件哈希；若基带检查失败，实际不会读取四个目标进行兼容判断。日志却统一描述为没有匹配文件，丢失了失败原因。
- `module/service.sh` 等待 boot_completed 后只维持框架配置，不重试专项挂载。
- `src/ApplyCarrierOverride.java` 的 `fullFiles` 接受表内原始文件和专项文件；`full` 决定展示字段，但两种情况下选择的框架六项相同。因此 full 不能代表专项能力已生效。

[KernelSU 官方说明](https://kernelsu.org/guide/module.html)将 post-fs-data 放在 Zygote 前，说明此阶段阻塞启动、最多等待约 10 秒，且默认使用 BusyBox standalone。官方当前文档不等于该现场版本的每项实现，新增 post-mount 等阶段前仍须核对所装版本及 Magisk 分支。

[AOSP GsmCdmaPhone](https://android.googlesource.com/platform/frameworks/opt/telephony/+/master/src/java/com/android/internal/telephony/GsmCdmaPhone.java)在异步基带响应处理中调用 `setBasebandVersionForPhone`；[TelephonyManager](https://android.googlesource.com/platform/frameworks/base/+/eb5712abd209dd51846bb53dc9203755e8b43bfb/telephony/java/android/telephony/TelephonyManager.java)展示其属性写入路径。结合现场时间线，早期阻塞等待 gsm.version.baseband 可能阻止提供该值的阶段前进。它是结构性时序风险，而非把 sleep 改大就能解决的问题。

## 建议的动态适配方案

### 1. 首先只修诊断和状态语义

把判断改为可解释的结果，保留全部现有安全守卫。每组分别记录：平台是否支持、基带值是否缺失/不完整/未知/混合、每个目标是否存在及可读、命令返回码、原始允许哈希或载荷哈希、源完整性、namespace、阶段、单调时间、尝试次数、最终停止原因。日志不记录 SIM 身份。

状态按开机代次及模块 manifest 摘要关联，原子写入；读取旧代次、缺字段或权限不足时显示“未知/过期”，不沿用上次成功。开机时间与运行时最近观察时间分开。只保留有界摘要，不能每分钟堆积完整日志。

### 2. 状态机与有界重试

每组使用 `checking → waiting / rejected / ready → preparing → mounted → verified`；失败转 `rolled_back` 或 `rollback_failed`，安全窗口已过转 `deferred`。两个组独立检查，但维持现有事务失败时逆序撤销本次所建挂载的原则。

| 条件 | 动作 |
| --- | --- |
| 模块、清单、守卫或载荷完整性不符 | 立即拒绝；不重试、不挂载 |
| 基带未知、混合或任何槽位未确认 | 禁止专项；缺失/不完整可以有界重新观察，但不先挂载 |
| 文件暂时不存在、分区未出现或可重试读取错误 | 仅在允许的早期窗口内短重试；每次重新验证身份和内容 |
| 文件可读但哈希未知、目标被其他模块改变 | 停止本次尝试；不因等待而放宽允许项 |
| 早期窗口结束或消费者可能已经读过 | 标记 deferred，运行时只读复核；不自动补挂 |
| 回滚失败 | 保留镜像、记录残留及错误，停止全部后续修改 |

初始候选可用 0/0.2/0.5/1 秒的少量探测，总预算不超过 2 秒；这是待测参数，不是已验证时限。应包括哈希和子命令耗时，设置可中断的总期限，达到期限后不得继续后台挂载。任何阻塞 I/O 都可能使纯 shell 时限失效，需在实现时验证 watchdog 与清理行为。**这只缓解文件短暂未就绪，不能解决等待后置基带属性的依赖。**

### 3. 挂载阶段必须由基带身份证据与首次读取时机共同决定

当前建议保留“基带尚未确认就不加载”，不把 service.sh 或 boot_completed 改为自动补挂器。post-mount 可用于处理其他模块覆盖顺序，但不能让电话进程尚未生成的属性提前出现，也不能假定它发生在所有原生消费者之前。

长期可研究更早、可靠的基带验证来源，例如针对已审计固件建立“实际选中 modem 镜像摘要 → 精确基带版本”的登记表。必须先证明启动槽位、实际引导镜像、镜像切换/回退与运行基带之间的对应关系，逐次校验当前选中内容，并在运行后交叉核对。不得把 build ID、ro.bootloader、同一型号、上次运行成功记录或未经核实的厂商属性当作当前基带证明。现阶段没有完成这项审计，不能用它替代现有基带守卫。

若无法在首次读取前可靠确认基带，也没有被验证的无中断重载协议，应明确保留专项跳过；仅提示“当前兼容检查通过，本次未加载”。简单重启仍可能重复同一时序，不能承诺下次启动自然解决。

动态适配应是选择已审计的精确配置记录，不是在线猜测或修改未知 vendor 二进制。记录包含设备/固件约束、全部基带槽位规则、两组原始文件允许摘要、发布载荷摘要和读取阶段证据；新增固件须单独审阅。框架继续只处理国内允许订阅和现有正确类型的六项键，persistent=false，维持 SIM、通话空闲与回读检查。

## 如何可靠确认加载

状态输出拆开以下事实，停止用单个 full 表示它们都成立：

| 字段建议 | 事实与判定方式 |
| --- | --- |
| compatibilityNow | 当前观察到的基带及目标内容是否被允许；注明观察 namespace，不解释成挂载成功 |
| bootMount | 本次启动每组/每文件的 skipped、mounted、already_mounted、already_identical、failed、rollback_failed，以及具体原因 |
| consumerView | 在已确定的真实读取进程 namespace 中，目标路径实际解析到什么内容及挂载；未确定读者则 unknown |
| consumerLoad | 读取事件、进程缓存/导出版本、厂商日志或受支持查询是否证明消费了该内容；仅路径可见时为 unproven |
| frameworkReadback | 订阅范围内六项配置的实际值、时间、是否写入及是否匹配 |
| businessValidation | IMS 注册及用户另行授权的 VoLTE/VoNR/VoWiFi/原生视频等真实业务结果、网络条件与时间；未测为 not_tested |

建议用户显示：“专项文件：本次未挂载；当前兼容检查通过；框架参数：6/6；专项加载及业务效果：未验证”。旧 fullBaseline 如需过渡兼容，明确标为弃用的兼容检查结果，并同时提供新字段；不得继续单独展示“完整加载”。

验证消费者视图时：

1. 从 init 配置、平台运营商配置包、日志及必要的授权读取跟踪确定真正读者与真实路径。本次 `mPlatformCarrierConfigPackage=com.google.android.carrier`；不能只选 system_server 或电话进程，也不能假定四个路径就是实际数据来源。
2. 记录 PID、启动时间和 namespace inode，检查前后复核，防止进程退出或 PID 重用。用 `/proc/PID/mountinfo` 精确解析字段 5；同时解析上级目录挂载、覆盖层和共享传播。权限拒绝单列 unknown。
3. 从 `/proc/PID/root/目标路径` 读取 SHA256，与完整性清单中的专项载荷比较，再比对目标和会话镜像的设备号、inode、mount root/ID、文件上下文、大小与只读属性。mountinfo 的 source 字段常是 tmpfs，不能凭 source 字符串认定镜像来源。
4. 必要时只在经核实支持的隔离子进程中进入目标 mount namespace 做只读检查，不向消费者 namespace 注入或补挂。SELinux 权限以消费者实际读取证据确认，root 可读不代表目标进程可读。
5. 对已有打开 FD/mmap 的进程核对其实际对象；替换路径不会更新旧 FD、mmap、已经解析的数据库或基带内存。没有读取记录或加载版本证明，就只报告“进程可见指定字节”。

[AOSP CarrierConfigLoader](https://android.googlesource.com/platform/packages/services/Telephony/+/master/src/com/android/phone/CarrierConfigLoader.java)会合并缓存的默认应用、运营商及覆盖配置，框架回读无法单独归因到某个 PB。应选已审计且未由本模块六项覆盖的可区分内容，结合配置提供者读取证据核对；若最终合并或运营商覆盖使其无法区分，继续报告 unknown，不为验证而写测试键。

## 实施顺序与验收

1. **诊断与展示先行**：补分项原因和开机代次，修正 full 的含义；先做离线 fixture，不改手机运行逻辑。覆盖空值、逗号空字段、双槽混合、命令失败、文件暂缺/未知、PID 更替、过期状态及权限拒绝；验证所有拒绝路径零挂载。
2. **确认数据读者和阶段**：用户另行授权后，在一次计划启动中记录单调时间线：脚本每次观察、基带属性每槽状态、真实文件和 namespace、消费者启动及首次读取。跟踪只针对目标读取，不长期采集完整通信日志。现场现有日志已显示约 12 秒间隔，但尚缺早期属性快照和首次成功读取证据。
3. **评审早期身份方案**：若能审计 modem 镜像与运行版本关系，再设计前置选择及最小重试；否则保留专项跳过。任何新阶段必须分别验证 KernelSU 和 Magisk 行为，不能以通用文档替代实测。
4. **候选版本验证**：原始/已替换/冲突文件、两组独立选择、第二项失败、跨组失败、信号中断、回滚失败、幂等及并发锁均做离线测试；再在另行授权的计划启动中验证全局和消费者视图、读取证据以及禁用后恢复。发现其他挂载时不覆盖或卸载别人的对象。
5. **业务验证另行授权**：先确认注册与网络条件，再验证实际呼叫、Wi-Fi 通话、VoNR及原生视频；不把配置开关、IMS 注册或静态测试当作全部业务通过。回滚已被消费者读取的内容可能仍需计划重启才能清除缓存，因此不能承诺仅 umount 即恢复运行行为。

初次研究属于源码研究与设备只读证据；未证明替代早期基带来源、首次读取路径、晚挂载重载效果或真实通信业务，未执行这些动作。

dev2 的计划启动还揭示了第二个属性时序问题：cbd.rc 在 fs 阶段先写 vendor.cbd.partition=modem，post-fs-data 之后才执行 ro.boot.slot_suffix 动作补成 modem_a/modem_b。该版本因此在 8.89 秒误拒绝，尚未进入内容校验。dev3 接受该已证实的过渡值；实际身份仍由当前槽位对应的只读挂载块设备和完整摘要决定，绝不以 modem 字符串本身放行。

dev3 随后的授权实机启动已通过：8.65 秒记录该过渡值，9.06 秒完成早期身份核验，9.21 秒完成四项挂载；Zygote、CBD、RIL 随后才启动。在六个目标进程的文件视图中验证了全部挂载、载荷 SHA256 与镜像 inode。运行基带交叉检查及六项框架回读通过。本次“无法早期挂载”已修复；真实配置读取及通信业务仍不等同于挂载通过，边界和详细记录见 [验证记录](VALIDATION.md)。
